# Compatibility

Status: CURRENT. This page says how far each tested game, and each part of the PSP, gets in Nakagawa Recomp today,
and which issue tracks the rest. Nakagawa never fakes what it can't do yet: when a game needs something that isn't
supported, it stops and names the missing piece. This page lists those stopping points.

## Status words

Every row below uses one of these words, except Hot Shots Tennis, which shows its rating from the player (see below).
A row claims only what its recorded evidence shows, and no other document can raise it.

The player doesn't show these words. Each game's page in the player shows a rating instead: **Perfect**,
**Playable**, **In-game**, **Menu**, **Title screen** or **Won't boot**, with a plain sentence on what to expect
([#1297](https://github.com/Jstar269/nakagawa-recomp/issues/1297)). A status word describes the project's own test
route, so on its own it gives a game only the rating in the table below. A game whose own run in the player has been
recorded gets the rating from that run instead; Hot Shots Tennis is **Playable**. The player's developer view still
shows the status word. `src/player/ui/scr_title.c` holds the same mapping, and
`mingw32-make nk-ui-player-screens-selftest` checks that the two agree.

| Status | Player tier | Meaning |
| :--- | :--- | :--- |
| Works | Perfect | The maintainer checked it on a documented route; the row says what that route covers. |
| Partially works | In-game | Some named parts are checked; the row says what is missing or refused. |
| Boots to a named boundary | Title screen | On the documented route it starts, then stops at a part Nakagawa doesn't support yet and says which part. |
| Not started | Won't boot | Nothing is built for it yet. |
| Experimental | No tier | A retail game someone has seen start or run, which the maintainer hasn't checked. |
| Untested | No tier | A retail game no one has reported on. |

One rule covers retail games. A game the maintainer has tested on a documented route keeps exactly the status its
recorded evidence supports. Every other retail disc is **Experimental** or **Untested**, as defined above. The
**EXPERIMENTAL** badge the player puts on an imported disc only means no one knows yet how well it runs; it doesn't
set a status here.

## Subsystem compatibility

Each row comes from the maintained engineering contracts and the live GitHub issues. Where an API or feature isn't
supported, Nakagawa Recomp stops at a named point instead of pretending it worked.

| Graphics / GE | Partially works | Frames and in-game 3D scenes are drawn with SDL3 and Vulkan, with a software rasterizer as a fallback; drawing straight to the framebuffer is checked by `display-smoke-v1`. A vertex with a non-finite clip position, screen position or lit colour (NaN or infinity) is dropped on both rasterizer paths and counted (`GESTAT+ ... nonfinite=`, `GEGPU stats: ... nonfinite=`), instead of being drawn from a host `(int)NaN` conversion or handed to the Vulkan clipper as a NaN `gl_Position`, because what the PSP's GE does with such a vertex hasn't been measured. Both paths share one rule (`ge_vtx_finite`), applied where vertices are captured, so it also covers through-mode and patch/spline inputs that have no earlier per-vertex check. Those vertices come from out-of-range arc-sine inputs reaching the bone matrices. On PSP-3000 hardware, 12 sampled out-of-range words were measured to return the same signed invalid NaN as the shared runtime helper (the two in-range endpoints return themselves) ([#69](https://github.com/Jstar269/nakagawa-recomp/issues/69)); the GE's own handling of the resulting non-finite vertex stays unmeasured. The one-frame skinned-character glitch at the switch to the main menu was fixed in [#822](https://github.com/Jstar269/nakagawa-recomp/pull/822) (traced to the VFPU3 compare decode; [#69](https://github.com/Jstar269/nakagawa-recomp/issues/69) closed 2026-10-20). Moving vertex transform and lighting to the GPU waits on GE correctness and CPU cost measurements ([#318](https://github.com/Jstar269/nakagawa-recomp/issues/318)), and a real-PSP pixel and command conformance corpus is in progress ([#343](https://github.com/Jstar269/nakagawa-recomp/issues/343)). | [#69](https://github.com/Jstar269/nakagawa-recomp/issues/69), [#318](https://github.com/Jstar269/nakagawa-recomp/issues/318), [#343](https://github.com/Jstar269/nakagawa-recomp/issues/343) |

### Issue #299: libfont registry import boundary

`sceRegOpenRegistry` (NID `0x92e41280`, library `sceReg`) and the rest of the `sceReg` family run against a read/write virtual system registry, opened in mode 1 (read) or mode 2 (read/write). Its `/CONFIG` tree (the category and key names, types, sizes and listing order) was measured on a PSP-3000 running 6.6.1 on 2026-10-09 with a read-only listing, as were the not-found (`0x8008271D`) and bad-handle (`0x8008272E`) codes and the fact that opening a missing category creates it.

Only six non-personal values were captured: language, both `button_assign` keys, date format, time format and summer time. Every other key, including personal ones such as the nickname (`/CONFIG/SYSTEM/owner_name`), passwords and network or account keys, is present with a neutral placeholder (0, an empty string, or zero bytes), never a real value, and a game that reads a placeholder is named once in the log. The player has no nickname setting yet. `sceUtilityGetSystemParamInt` reads the registry's shared keys, so a setting a game writes is the value both report.

Writes need a mode-2 handle. A game can create keys and categories, and remove empty categories it created, but the measured categories can't be removed. `sceRegFlushCategory` and `sceRegFlushRegistry` save every change in one safe step to a per-user overlay file (`registry/system.json` in the per-user data folder, or `SR_SYSTEM_REGISTRY`). A corrupt overlay is reported, ignored and moved aside on the next save; it never crashes the game. The write rules and the remaining error codes are project-authored from the public PSPSDK documentation and public homebrew behaviour and are not hardware measured, because the console probe never writes the registry. Unknown keys still fail closed by name, and `sceRegRemoveKey` (no public argument documentation), `sceRegRemoveRegistry` and `sceRegExit` are still unimplemented.

Starting a module that is already started returns `SCE_KERNEL_ERROR_ALREADY_STARTED` (`0x80020133`), matching the public [PSP kernel error table](https://github.com/pspdev/prxtool/blob/master/pspkerror.C). This value comes from that source, and it and the rule for restarting a stopped module haven't been checked on real hardware; whether a stopped module can restart is an inference.

## Library sweep scoreboard

This section is for contributors who run `tools/library_sweep.py` over a library of discs.

The sweep can write a machine-readable summary with no game titles in it, both while a run is going and after it
ends. `coverage.iso_count` is the number of discs found; `coverage.recorded_routes` is how many of them the summary
covers so far. The summary reports the source identity, the time budget, coverage, the stage each disc reached, the
blockers, library-family counts, and a comparison with the previous run. It must not contain game titles, disc IDs,
source keys, file names or individual NIDs. NID family counts use only the public vocabulary built from
`tools/nid_corpus.json`, and any other input value is left out. Every blocker class that occurred is listed, drawn from
the fixed public bring-up vocabulary and the runner's named timeout and error points, sorted by count (highest first)
and then by code; a code the runner doesn't know fails closed.

A later run can compare itself with an earlier summary through `--previous-public-output`. That file is a
user-supplied prior progress claim and is not cryptographically authenticated: the runner checks its structure and
that it is consistent with itself, so only use a summary made by a trusted prior run. The runner rejects an input
with unknown issue numbers, or with any other unknown or title-specific field, before comparing. Issue references
come from the checked-in schema allowlist that the public `nk_cli.py` report generator also uses; nothing is looked
up online.

Each game's bring-up launch (the recompiled game actually running) is limited by `--launch-timeout SECONDS`: 1 to
120, the same range `nk_cli.py bringup --launch-timeout` accepts, with a default of 20. A value outside that range is
rejected before any game runs. `--time-budget` still limits each game's whole route (inspect, import, analyze,
codegen, compile, package and launch), so the launch limit passed to bring-up is
`min(--launch-timeout, --time-budget)`, and the default gives the earlier fixed `min(20, --time-budget)`. To let
games run for 60 s or 110 s, raise `--launch-timeout` and give `--time-budget` enough room for the build stages too.
The summary records `time_budget_seconds` but not the launch limit, so only compare summaries made with the same
`--launch-timeout`.

Runs split across several shards are combined with `--merge-private-reports PATH [PATH ...]`. Each argument can be the
shard's `library-sweep.json` file or its private folder (the `--private-dir` the shard ran with), and you can mix the
two in one command. The merge checks every shard report the same way a single run does, then writes one private
report and one title-free summary to `--private-dir` and `--public-output`. A folder without `library-sweep.json`, a
missing file, a report that is too large or malformed, or a report with an unsupported schema fails closed with a
message that names the path and the reason in plain words; it never prints the file's contents.

`--title-manifests DIR` gives each game's route your own title manifests that name its disc ID (copied into the
route's `user-data/manifests`), the same title list the player reads. A game whose data ships in archives on the disc
is then set up by bring-up through the player's staging step in that route's user-data folder before it starts, so
the player executable must be built. Staging and building a package for a large disc can take several minutes; raise
`--time-budget` for such games.

The sweep reads JSON from outside through the bounded parser. Per-game bring-up reports and import sidecars allow
32 MiB, 32 levels, 262,144 object members and comma-separated items, and 1,048,576 structural nodes, because their
import lists grow with the game. The private resume report allows 64 MiB, 32 levels, 1,048,576 members and items, and
4,194,304 nodes, because it holds one row per ISO; a test round-trips 10,000 detailed rows in a report larger than
1 MiB under these limits. The writer applies the same resume limits before replacing either output, so it can't leave
a checkpoint its next run would reject. A bring-up report over its limits is treated as a route with no report, and
an over-limit sidecar is ignored before the usual build-report and runtime fallback. The previous public summary
uses the shared 1 MiB cache budget, because its checked schema is small and title-free. Duplicate fields, invalid
UTF-8, non-finite numbers, malformed JSON and exceeded limits are rejected; `build-report.json` keeps its own 4 MiB
build-report budget.

The `ratchet.furthest_stage_high_water` values are high-water marks. They can go up when the source identity, route
budget and ISO count match the previous summary, and they never go down during that comparison. `coverage` and the
blocker fields describe the current run and are for diagnosis only. If the source identity, route budget or ISO count
changes, the comparison reports `NEW_BASELINE` and starts a new high-water baseline instead of mixing results that
can't be compared. A run with no previous summary reports `NO_BASELINE`.

The comparison is a title-free progress signal. It doesn't prove full compatibility for any retail game, stable
in-game input, PSP timing, picture accuracy or hardware correctness; each of those needs its own evidence.
