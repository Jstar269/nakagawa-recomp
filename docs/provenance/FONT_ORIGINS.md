# PGF replacement-font origins (engineering provenance)

This is an engineering record, not legal advice. Every origin claim below carries a URL + commit/hash, or is marked
UNKNOWN. No PGF payload, upstream PGF source file, or retail-derived data is
added by this record: the four payloads remain excluded by
`assets/public_source_profile.json` (`font/*.pgf`). Public builds read fonts
through the project-authored reader (`src/rt/pgf_public.c`, #349). Section 8 records the separate project UI fonts (TTF, SIL Open Font
License); they are not PGF replacements or game data.

## 2. Method

- Partial clone (`--filter=blob:none`) of PPSSPP, then `git cat-file -p
  <rev>:assets/flash0/font/<name>` for the pin and each historical revision.
  Blob fetches completed, so parses below are from exact upstream bytes.
- `git log --follow --format="%H %ad %s"` per font path for the full binary
  history.
- PGF header parse per PPSSPP `Core/Font/PGF.h` (`struct PGFHeader`, packed):
  `u16 headerOffset @0`, `u16 headerSize @2`, `char magic[4] @4`,
  `s32 revision @8`, `s32 version @12`, `char fontName[64] @53`,
  `char fontType[64] @117`, `u16 firstGlyph @182`, `u16 lastGlyph @184`.
  All four pinned payloads: `headerSize 392`, magic `PGF0`, revision 2,
  version 6.
- PPSSPP issues/PRs read via the GitHub API: #13588 (jpn0 rework), #13589 /
  #13590 (ltn0–7), #13718 (ltn8–15 tool chain — the thread that names the
  converter tools), #13721 (small-latin change), #13190 (kr0), #13753 (all-PGF
  fix round), #13510 (motivating Gundam glyph issue for the October 2020
  regeneration).

Conclusions:

1. **The true outline sources are Source Han Sans (jpn0, kr0) and Ume Hy
   Gothic (ltn0, ltn8).** The pre-camouflage headers name them directly, and
   every byte revision from Nov 2020 to the pin is a same-lineage edit by the
   same contributor (nassau-tk), not a source swap: sizes evolve continuously
   (jpn0 4,351,908 → 4,353,284 → 4,417,412 → 4,316,284) with no discontinuity
   consistent with re-sourcing.
2. **The pinned names are deliberately false.** Commit `dc34bea8d4dee77629da3cbaedc83fc8c05af159`
   says so itself ("camouflage the Font name"). FTT-NewRodin is a Fontworks
   retail family; AsiaKNHH-SONY-uni names Sony. Those strings are not evidence
   of Fontworks/Sony outlines, and redistributing the payloads under those
   names would misattribute Ume/Adobe outlines to Sony/Fontworks (§5).
3. **Manual-edit chain is admitted by the author**: full manual rework of 2,946
   JIS level-1 kanji (#13588), glyph position/size passes through 2023, and
   hex-editor patching of ascender/descender fields (#13718). The payloads are
   therefore Modified Versions of their sources in the OFL sense, not verbatim
   conversions.

## 4. Conversion tool chain (as stated by the contributor)

From nassau-tk's notes in PPSSPP #13718 (2020-11-26) and #13589:

- TTF → PGF conversion: [pgftool](https://github.com/tpunix/pgftool) (C tool
  by tpunix; `dump_pgf -h` used to check `max glyph width 16 / max glyph
  height 14`, resizing the TTF and reconverting until the values match), and
  `ttf2pgfj.exe` for ltn0/2/4/6 (fixed width/height converter; author asked
  for "the converter which can be changed to the proper width and height").
- Glyph shaping: a font editor (FontCreator-class application named in
  #13718), manual per-glyph size/position/shape work.
- Metric patching: hex editor on the generated PGF (offsets `0xd4` ascender /
  `0xd8` descender in 26.6 fixed point; small-latin target ascender
  9.000000–10.000000, descender −2.000000 to match official PGF metrics).
- Reference: the author's own real-PSP dumps ("you must get the original pgf
  files from your own real PSP") used as metric targets — a workflow note,
  not a claim that retail bytes are inside the payloads (headers, sizes, and
  the conversion narrative all indicate regenerated bitmaps).

Tool licence status: pgftool carries **no licence file** (single-merge repo,
HEAD `a9b3114`; verified by clone 2026-09-17), so its terms are UNKNOWN —
all-rights-reserved by default. Tool licensing does not automatically
encumber output files, but this project must not adopt pgftool code. The project-owned converter is
specified in `docs/cleanroom/PGF_CONVERTER_SPEC.md` and implemented in
`tools/pgf_writer.py` and `tools/ttf2pgf.py` (#313): written from a behaviour
specification, not from any emulator or tool source. `ttf2pgfj.exe`
provenance/licence: UNKNOWN (flagged, not used).

## 5. Licence terms

### 5.1 Source Han Sans (jpn0, kr0) — SIL Open Font License 1.1

Verified text: <https://github.com/adobe-fonts/source-han-sans/blob/release/LICENSE.txt>
(`release` branch; "Copyright 2014-2025 Adobe …, with Reserved Font Name
'Source' … licensed under the SIL Open Font License, Version 1.1").
Operative conditions for a converted/redistributed PGF:

1. **No sale by itself** (OFL §1): the PGF may not be sold standalone; bundling
   with software is permitted.
2. **Notice + licence with every copy** (OFL §2): each copy must contain the
   above copyright notice and the licence, as stand-alone text files,
   human-readable headers, or viewable machine-readable metadata. PPSSPP ships
   neither alongside the PGFs; this tree ships neither either (payloads
   excluded, so no text is owed today — but see the RULE below).
3. **Reserved Font Name 'Source'** (OFL §3): no Modified Version may use the
   RFN as its *primary font name as presented to users* without Adobe's
   written permission. The Nov–Dec 2020 payloads named "Source Han Sans" as
   their PGF `fontName` while being Modified Versions (manual kanji rework).
4. **No promotion by holder names** (OFL §4); **stay under OFL** (OFL §5): the
   font, modified or not, in part or whole, must be distributed entirely under
   OFL and no other licence. A GPL notice must therefore never be applied to
   the font payloads themselves; the project GPL covers the surrounding work,
   and the OFL payloads would sit alongside as a separately-licenced
   aggregate element with their own texts.
5. Source Han Sans input version, variant file (Super OTC vs JP/KR subset)
   and weight file: UNKNOWN. nassau-tk never named the input file and no byte
   or glyph comparison has been made, so conversion dates do not narrow the
   candidates: any release published before the conversion, an intermediate
   checkout, or another variant remains possible.

## 6. Project font slots

The opaque PGF route remains excluded. The project builds its Japanese, Latin,
and Korean slots from pinned OFL sources with the project-owned converter
(`tools/ttf2pgf.py`, `tools/pgf_writer.py`) and public PGF reader
(`src/rt/pgf_public.c`). Each generated file is a project conversion, not a
claim that it is an authentic firmware font.

The project builds one open Latin fallback (`nkltn.pgf`). It does not bundle
firmware Latin files: `ltn0.pgf` through `ltn15.pgf` stay in the user's local
font cache when imported. The runtime's per-index source and fallback order is
documented in [`SETUP.md`](../SETUP.md#system-fonts).

### 6.4 Korean slot

Nanum Gothic was evaluated first from Google Fonts commit
[`c1eda9233c33ad7775b27efd794f931095cf6133`](https://github.com/google/fonts/tree/c1eda9233c33ad7775b27efd794f931095cf6133/ofl/nanumgothic).
Its Regular TTF is 2,054,744 bytes with SHA-256
`76f45ef4a6bcff344c837c95a7dcc26e017e38b5846d5ae0cdcb5b86be2e2d31`; its
adjacent licence is SIL OFL 1.1 and declares no Reserved Font Name. It maps
11,697 of the assigned 11,951 Korean points, missing 254, so it was not
selected despite its smaller source file.

The selected fallback is Gowun Dodum Regular, pinned from Google Fonts commit
[`c1eda9233c33ad7775b27efd794f931095cf6133`](https://github.com/google/fonts/tree/c1eda9233c33ad7775b27efd794f931095cf6133/ofl/gowundodum):

| Input | Upstream size / SHA-256 | Pinned local size / SHA-256 |
| --- | ---: | --- |
| `GowunDodum-Regular.ttf` | 7,229,088 / `a6e457933227483a11758fd0947bc74422a106d46f0bf057fdaa5af94a30067d` | 7,229,088 / `a6e457933227483a11758fd0947bc74422a106d46f0bf057fdaa5af94a30067d` |
| `OFL.txt` | 4,395 / `a7c73f9521cd646bbdfb6684c99a62311bbd7bce11898dc11ef0b3c69eda1aca` | 4,394 / `3e5acd28c1f57250f9486bd280b9f268c563687543f25a186c632a56400bbc25` |

The downloaded licence is SIL OFL 1.1 and declares no Reserved Font Name;
`PIN.json` records an empty list, matching the upstream text. The local licence
removes one trailing ASCII space on line 22 without changing licence wording.
The selected font covers all 11,951 assigned points. The converter's denied
source-name markers are also avoided: the PGF uses the project-owned name
`Nakagawa Open Korean` and style `Regular`.

At the target 12 ppem, a converter-generated software sample of ASCII `A`,
Hangul U+AC00 and U+D55C, and jamo U+3131 is legible in both candidate Regular
faces. Gowun Dodum is selected for its complete assigned coverage, not its
larger binary size. This visual check does not establish PSP hardware output.

The built-in Korean text repertoire is decoded from Python's standard
`euc_kr` codec: ASCII U+0020-U+007E (95), assigned cells in KS X 1001 rows 1-4
and 6-9 (684 symbols, punctuation, full-width forms, and jamo), and all 11,172
modern precomposed Hangul syllables U+AC00-U+D7A3. The 2,350 Hangul syllables
from KS X 1001 rows 16-40 are contained in the modern range. This gives 11,951
unique points with canonical SHA-256
`50596a7f6e0e5158561147eae40a38edc12c28b1a4be3efff6d717c74b638bc4`. Hanja
rows are out of scope. Roman numerals (row 5), Japanese kana (rows 10-11), and
Greek/Cyrillic (row 12) are outside this Korean-text repertoire.

The 12 ppem PGF is named `nkkr.pgf`. Its sparse character map spans
U+0020-U+FFE6 with 65,479 entries and 11,951 glyph pointers. The public native
reader accepts this image; a small native round-trip fixture verifies the
high code point, Hangul, and absent-code behavior. Two independent builds
produced identical PGF bytes:

| Output | Size | SHA-256 |
| --- | ---: | --- |
| `nkkr.pgf` | 987,672 bytes | `193ddfcbc9053d1c5941019c4cd42170c64d8a4dcdb22456d9cf2f611fd224a1` |
| `nkkr.json` | 6,922 bytes | `fda03c0988b8f4a3fce4755b66104eb1730e587702965e6e30bf9edb93fd56b7` |

The selected 7.2 MB source is larger than Nanum Gothic because it covers the
entire assigned set. The remaining import path keeps a user's own Korean font
ahead of the project fallback.

The reader now refuses a `char_map_count` larger than the inclusive header
range `last - first + 1`. Before that bound, a malformed map count could expose
padding as a drawable code after the declared last point. Smaller map counts
remain valid. The Korean PGF's 65,479 map entries match U+0020-U+FFE6 exactly
and remain accepted even though the map is sparse relative to its 11,951 glyph
pointers.

RULE (licence-text hygiene): the OFL text stays alongside the generated build
payload. It is not added under `THIRD_PARTY_LICENSES/` unless a corresponding
payload is admitted to the public source tree.

Geist, Geist Mono, and Noto Sans JP are static instances of their variable
sources, generated with fontTools 4.67.0 using
`fontTools.varLib.instancer --static --update-name-table --no-recalc-timestamp`
and the listed `wght` value. This keeps fixed weights available to SDL3_ttf
without a font-generation build dependency.

full coverage so Japanese user title metadata is not narrowed to a test subset.
The upstream metadata declares the Reserved Font Name `Source`; the shipped
family name remains `Noto Sans JP`.
