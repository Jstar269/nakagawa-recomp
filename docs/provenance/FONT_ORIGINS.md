# PGF replacement-font origins (engineering provenance)

This is engineering evidence for qualified review, not legal advice or legal
clearance. Every origin claim below carries a URL + commit/hash, or is marked
UNKNOWN. No font payload, upstream source file, or retail-derived data is
added by this record: the four payloads remain excluded by
`assets/public_source_profile.json` (`font/*.pgf`), and the fail-closed PGF
boundary (`src/rt/pgf_unavailable.c`) stays in force.

Analyst note: I am an engineering-provenance analyst, not a lawyer. Section 6
lists the questions that genuinely need counsel.

## 2. Method

- Partial clone (`--filter=blob:none`) of PPSSPP, then `git cat-file -p
  <rev>:assets/flash0/font/<name>` for the pin and each historical revision.
  Blob fetches completed, so parses below are from exact upstream bytes.
- `git log --follow --format="%H %ad %s"` per font path for the full binary
  history.
- PGF header parse per PPSSPP `Core/Font/PGF.h` (`struct PGFHeader`, packed):
  `u16 headerOffset @0`, `u16 headerSize @2`, `char magic[4] @4`,
  `s32 revision @8`, `s32 version @12`, `char fontName[64] @53`,
  `char fontType[64] @117`, `u16 firstGlyph @182`, `u16 lastGlyph @184`.
  All four pinned payloads: `headerSize 392`, magic `PGF0`, revision 2,
  version 6.
- PPSSPP issues/PRs read via the GitHub API: #13588 (jpn0 rework), #13589 /
  #13590 (ltn0–7), #13718 (ltn8–15 tool chain — the thread that names the
  converter tools), #13721 (small-latin change), #13190 (kr0), #13753 (all-PGF
  fix round), #13510 (motivating Gundam glyph issue for the October 2020
  regeneration).

Conclusions:

1. **The true outline sources are Source Han Sans (jpn0, kr0) and Ume Hy
   Gothic (ltn0, ltn8).** The pre-camouflage headers name them directly, and
   every byte revision from Nov 2020 to the pin is a same-lineage edit by the
   same contributor (nassau-tk), not a source swap: sizes evolve continuously
   (jpn0 4,351,908 → 4,353,284 → 4,417,412 → 4,316,284) with no discontinuity
   consistent with re-sourcing.
2. **The pinned names are deliberately false.** Commit `dc34bea8d4dee77629da3cbaedc83fc8c05af159`
   says so itself ("camouflage the Font name"). FTT-NewRodin is a Fontworks
   retail family; AsiaKNHH-SONY-uni names Sony. Those strings are not evidence
   of Fontworks/Sony outlines, and redistributing the payloads under those
   names would misattribute Ume/Adobe outlines to Sony/Fontworks (§5).
3. **Manual-edit chain is admitted by the author**: full manual rework of 2,946
   JIS level-1 kanji (#13588), glyph position/size passes through 2023, and
   hex-editor patching of ascender/descender fields (#13718). The payloads are
   therefore Modified Versions of their sources in the OFL sense, not verbatim
   conversions.

## 4. Conversion tool chain (as stated by the contributor)

From nassau-tk's notes in PPSSPP #13718 (2020-11-26) and #13589:

- TTF → PGF conversion: [pgftool](https://github.com/tpunix/pgftool) (C tool
  by tpunix; `dump_pgf -h` used to check `max glyph width 16 / max glyph
  height 14`, resizing the TTF and reconverting until the values match), and
  `ttf2pgfj.exe` for ltn0/2/4/6 (fixed width/height converter; author asked
  for "the converter which can be changed to the proper width and height").
- Glyph shaping: a font editor (FontCreator-class application named in
  #13718), manual per-glyph size/position/shape work.
- Metric patching: hex editor on the generated PGF (offsets `0xd4` ascender /
  `0xd8` descender in 26.6 fixed point; small-latin target ascender
  9.000000–10.000000, descender −2.000000 to match official PGF metrics).
- Reference: the author's own real-PSP dumps ("you must get the original pgf
  files from your own real PSP") used as metric targets — a workflow note,
  not a claim that retail bytes are inside the payloads (headers, sizes, and
  the conversion narrative all indicate regenerated bitmaps).

Tool licence status: pgftool carries **no licence file** (single-merge repo,
HEAD `a9b3114`; verified by clone 2026-09-17), so its terms are UNKNOWN —
all-rights-reserved by default. Tool licensing does not automatically
encumber output files, but this project must not adopt pgftool code; the
project-owned converter (`tools/pgf_build.py`) is written from the public
`Core/Font/PGF.h` layout and carries its own GPL-2.0-or-later header with a
PPSSPP-format-knowledge derivation line. `ttf2pgfj.exe` provenance/licence:
UNKNOWN (flagged, not used).

## 5. Licence analysis (licence texts verified, conclusions need counsel)

### 5.1 Source Han Sans (jpn0, kr0) — SIL Open Font License 1.1

Verified text: <https://github.com/adobe-fonts/source-han-sans/blob/release/LICENSE.txt>
(`release` branch; "Copyright 2014-2025 Adobe …, with Reserved Font Name
'Source' … licensed under the SIL Open Font License, Version 1.1").
Operative conditions for a converted/redistributed PGF:

1. **No sale by itself** (OFL §1): the PGF may not be sold standalone; bundling
   with software is permitted.
2. **Notice + licence with every copy** (OFL §2): each copy must contain the
   above copyright notice and the licence, as stand-alone text files,
   human-readable headers, or viewable machine-readable metadata. PPSSPP ships
   neither alongside the PGFs; this tree ships neither either (payloads
   excluded, so no text is owed today — but see the RULE below).
3. **Reserved Font Name 'Source'** (OFL §3): no Modified Version may use the
   RFN as its *primary font name as presented to users* without Adobe's
   written permission. The Nov–Dec 2020 payloads named "Source Han Sans" as
   their PGF `fontName` while being admitted Modified Versions (manual kanji
   rework) — that combination is exactly what §3 restricts. The Jan 2021
   camouflage removed the RFN exposure but replaced it with §5.2's problem.
4. **No promotion by holder names** (OFL §4); **stay under OFL** (OFL §5): the
   font, modified or not, in part or whole, must be distributed entirely under
   OFL and no other licence. A GPL notice must therefore never be applied to
   the font payloads themselves; the project GPL covers the surrounding work,
   and the OFL payloads would sit alongside as a separately-licenced
   aggregate element with their own texts. Whether that aggregation reading
   holds for a PGF the HLE loads at runtime is a counsel question (§6).
5. Source Han Sans input version: UNKNOWN. Bounded, not identified: the jpn0
   conversion (Oct–Nov 2020) postdates release 2.001 (2019-04-09) and overlaps
   release 2.002 (2020-11-04) per
   <https://github.com/adobe-fonts/source-han-sans/releases> tag dates; the
   kr0 conversion (Nov 30, 2020) postdates 2.002. Candidate set {2.001,
   2.002}, variant file (Super OTC vs JP/KR subset, weight file) UNKNOWN —
   nassau-tk never named the input file.

### 5.2 Ume Hy Gothic (ltn0, ltn8) — Ume-family licence (modified BSD)

- Project page: <https://osdn.net/projects/ume-font/wiki/FrontPage> lists
  梅Hyゴシック (Ume Hy Gothic) in the family and states (verified 2026-09-17):
  "These fonts are free software. Unlimited permission is granted to use,
  copy, and distribute it, with or without modification, either commercially
  and noncommercially. THESE FONTS ARE PROVIDED 'AS IS' WITHOUT WARRANTY."
- The family readme (`umeFont_readme`, mirrored e.g. at
  <http://harjes-metallkunst.de/media/fonts/umeFont_readme.html>) applies a
  **modified (3-clause) BSD licence** to the UmeFont family (verified
  preamble: "Redistribution and use in source and binary forms, with or
  without modification, are permitted provided that the following
  conditions are met"), with a clarification that non-font reuse such as
  document embedding is unrestricted. Full condition text (copyright-notice
  retention, condition reproduction, no-endorsement) was read on the mirror,
  not on the canonical OSDN download; exact Ume release/version converted:
  UNKNOWN.
- Redistribution of an Ume-derived PGF therefore requires preserving the Ume
  copyright notice and licence conditions — again, texts this tree does not
  ship today (payloads excluded), and PPSSPP does not ship either.

### 5.3 Trademark / misdescription (Sony / Fontworks names)

`FTT-NewRodin Pro DB`, `FTT-NewRodin Pro Latin`, and `AsiaKNHH-SONY-uni` are
product names of Fontworks Inc. and Sony. The pinned payloads contain Adobe
and Ume outlines under those names by admitted "camouflage". Redistributing
them byte-identical would publish false designation of origin; renaming the
header to an honest project-owned name is a further modification that must
then satisfy OFL §3 (avoid 'Source') and Ume attribution simultaneously.
Either direction needs counsel before any redistribution (§6).

## 6. Route decision

Among (1) redistribute PPSSPP payloads with notices, (2) generate our own
PGFs from pinned OFL sources with a project-owned reproducible converter,
(3) keep excluding and require user-supplied fonts:

- **(1) is rejected.** Notices alone cannot cure the false Sony/Fontworks
  designation, and honest renaming cannot be validated without the exact input
  releases (both UNKNOWN, §5.1/§5.2). Redistributing opaque third-party
  binaries whose inputs we cannot pin contradicts the project's
  byte-provenance standard (cf. `src/rt/atrac3p/PROVENANCE.md`,
  `assets/vfpu/PROVENANCE.json`).
- **(2) is the target.** `tools/pgf_build.py` (new, project-owned,
  GPL-2.0-or-later, format knowledge derived from PPSSPP `Core/Font/PGF.h`)
  emits deterministic PGFs (rev 2 / ver 6 header layout) from caller-supplied
  glyph tables, refuses Sony/Fontworks camouflage names, and records input
  SHA-256 + OFL/Ume notice obligations in its manifest output. It is a
  scaffold, not a production font pipeline: CJK-scale coverage, metric tuning
  (ascender/descender targets per #13718), and raster quality remain open
  engineering work. No payload is produced or committed by this change.
- **(3) is the interim.** Payloads stay excluded; users supply fonts locally
  (`SR_FONTDIR`), exactly as `font/README.md` documents. A converter-produced
  payload may only enter the tree after: pinned OFL inputs with SHA-256, OFL
  §2 texts shipped alongside, an honest non-RFN name, qualified review, and a
  path-specific provenance record.

RULE (licence-text hygiene): OFL/Ume licence texts may be added under
`THIRD_PARTY_LICENSES/` only when a corresponding payload is actually shipped
in the public tree. Nothing is shipped today, so no text is added today.

## 8. Questions that genuinely need a lawyer

1. May OFL §5 ("distributed entirely under this license") payloads be loaded
   at runtime by a GPL-3.0-or-later program without the combination becoming a
   derivative work of either, and does the answer change if the payloads ship
   in the same archive?
2. Does a PGF converted from Source Han Sans with 2,946 hand-reworked kanji
   still "use the Reserved Font Name" if its `fontName` field reads
   "Source Han Sans", and does renaming it to a project-owned name fully
   resolve OFL §3 without Adobe's written permission?
3. Does reproducing the official PGF header metrics (ascender 9.0, descender
   −2.0, glyph dimensions) and the official font-list names in a
   reimplementation risk circumvention or trademark exposure even with
   original outlines?
4. Is PPSSPP's "camouflage" rename itself an actionable false designation if
   mirrored, i.e. is byte-identical redistribution with Sony/Fontworks names
   categorically excluded even with full OFL/Ume notices?
